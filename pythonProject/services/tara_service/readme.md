# Tара API / сервис разбора отчетов по таре

## Назначение

Сервис нужен для:
- чтения отчета по таре из `pythonProject/downloads`
- разбора клиентов и их позиций
- сохранения результата в JSON
- поиска клиента по строке клиента
- автопроверки новых файлов по расписанию
- подготовки удобного внутреннего API для Telegram-бота

---

## Текущие файлы сервиса

### `parse_tara_report.py`
Основной парсер отчета по таре.

Что делает:
- берет входной файл **только** из `pythonProject/downloads`
- читает `.xls`
- использует правила из `tara_rules.json`
- определяет:
  - клиентские строки
  - строки номенклатуры
  - служебные строки
- сохраняет:
  - `tara_parsed.json`
  - `tara_bad_clients.json`
  - `tara_skipped_rows.json`
  - `tara_parse.log`

Особенности:
- не выдумывает общий итог клиента
- хранит `client_total_raw` как есть из строки клиента
- если явного итога нет, это не считается ошибкой
- `items_sum` считается отдельно
- поиск идет по **полной строке клиента**

---

### `tara_rules.json`
Файл правил классификации.

Содержит:
- `item_prefixes` — признаки номенклатуры
- `service_prefixes` — признаки служебных строк
- `header_words` — признаки шапки таблицы
- `org_markers` — признаки клиента-организации
- `manager_markers` — маркеры торговых представителей
- `item_groups.tara` — что считать тарой
- `item_groups.equipment` — что считать оборудованием
- `force_service_contains` — жесткие правила для служебных строк
- `force_client_contains` — жесткие правила для клиента
- `ignore_exact` / `ignore_contains` — исключения

Все списки редактируются без изменения кода парсера.

---

### `tara_auto_update.py`
Автообновление отчета по расписанию.

Что делает:
- ищет самый свежий файл отчета по таре в `pythonProject/downloads`
- запоминает последний успешно обработанный файл
- сравнивает новый файл с прошлым по:
  - пути
  - времени изменения
  - размеру
- если файл новый — запускает разбор
- если нового файла нет — пишет это в состояние и планирует повтор через 5 минут

Хранит состояние в:
- `tara_update_state.json`

В состоянии сохраняется:
- `last_processed_file`
- `last_processed_mtime`
- `last_processed_size`
- `last_processed_at`
- `last_check_at`
- `last_check_result`
- `last_missing_reason`
- `retry_scheduled_for`

---

## Структура выходных данных

### `tara_parsed.json`
Основной результат разбора.

Ключи:
- `source_file`
- `rules_file`
- `stats`
- `clients`
- `errors`
- `skipped_rows`
- `bad_clients`

### Пример клиента
```json
{
  "row": 610,
  "client": "Гензе Иван Давыдович ИП - Воротников",
  "client_total_raw": 18.0,
  "items": [
    {"row": 611, "name": "Бочка 30л", "total": 1.0}
  ],
  "items_sum": 18.0,
  "difference": 0.0,
  "is_total_match": true,
  "has_explicit_total": true,
  "total_source": "client_row",
  "warnings": []
}
```

## Ручной запуск

Из папки `pythonProject/services/tara_service`:

```bash
python parse_tara_report.py "Ведомость по переданной возвратной таре клиент - Прокопенко (XLS).xls"
```

Поиск клиента:

```bash
python parse_tara_report.py "Ведомость по переданной возвратной таре клиент - Прокопенко (XLS).xls" --find Гензе
```

Важно:
- в аргумент передается **только имя файла**
- сам файл должен лежать в `pythonProject/downloads`

---

## Автообновление

Плановое время:
- `10:31`
- `15:31`
- `17:01`

Логика:
1. найти самый свежий отчет
2. сравнить с последним обработанным
3. если новый файл есть — обновить JSON
4. если нового файла нет — записать причину
5. поставить повторную попытку через 5 минут

---

## Что считать ошибкой

Критичные ошибки:
- клиент найден, но у него нет номенклатуры
- у клиента есть явный итог в строке, но он не сходится с суммой позиций

Не критично:
- у клиента отсутствует явный итог в строке, если отчет сам так сформирован

---

## Поиск

Сейчас поиск работает по полю:
- `client`

То есть ищется подстрока по **полной строке клиента**.

Примеры:
- `Гензе`
- `Морозова`
- `Воротников`
- `Оловозаводская`

Это позволяет находить:
- по имени клиента
- по торговому
- по адресу

## Внутренний API для Telegram-бота

Правильный следующий слой — `tara_api.py`.

Он должен давать боту готовые функции, а не заставлять бота самому читать JSON.

Рекомендуемые функции:

```python
get_tara_report_data()
get_tara_report_summary()
find_tara_clients_api(query: str)
get_tara_client_report(query: str)
get_tara_update_status()
refresh_tara_report_manual()
```

### Назначение функций

#### `get_tara_report_data()`
Вернуть весь `tara_parsed.json`.

#### `get_tara_report_summary()`
Вернуть краткую сводку:
- сколько клиентов
- сколько строк
- когда было обновление
- есть ли проблемы

#### `find_tara_clients_api(query)`
Вернуть список клиентов по поисковой строке.

#### `get_tara_client_report(query)`
Вернуть готовую структуру для Telegram:
- найденные клиенты
- тара
- оборудование
- сумма по позициям
- итог в строке клиента
- источник итога

#### `get_tara_update_status()`
Вернуть состояние автообновления из `tara_update_state.json`.

#### `refresh_tara_report_manual()`
Запустить ручное обновление тары через ту же логику, что и по расписанию.

## Как Telegram-бот должен использовать сервис

Примеры сценариев:

### Кнопка: `Отчет по таре`
Использовать:
- `get_tara_report_summary()`

### Кнопка: `Поиск тары`
Использовать:
- `get_tara_client_report("Гензе")`

### Кнопка: `Статус обновления`
Использовать:
- `get_tara_update_status()`

### Кнопка: `Обновить тару сейчас`
Использовать:
- `refresh_tara_report_manual()`

## Принцип архитектуры

Бот не должен:
- сам читать xls
- сам искать по json
- сам решать, что является тарой или оборудованием

Это должен делать сервис тары.

Правильная схема:
- `parse_tara_report.py` — разбор
- `tara_rules.json` — правила
- `tara_auto_update.py` — обновления
- `tara_api.py` — интерфейс для Telegram-бота
